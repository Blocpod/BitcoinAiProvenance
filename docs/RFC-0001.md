# RFC-0001: Bitcoin-Anchored AI Provenance Receipts

**Status:** Implemented experimental specification  
**Version:** 1.0  
**Protocol release:** 0.1.0

## Purpose

This RFC defines signed, content-addressed provenance receipts for AI artifacts and autonomous-agent actions. Bitcoin is used as an immutable ordering and timestamp anchor for aggregated receipt roots.

The protocol does not claim that Bitcoin proves the truth, legality, quality, or ownership semantics of a signed assertion.

## Normative language

The words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are interpreted as requirements for conforming implementations.

## Canonical serialization

Implementations MUST serialize signed statements deterministically. Version 1 accepts JSON values consisting of null, booleans, valid Unicode strings, safe integers, arrays, and plain objects. Object keys MUST be sorted lexicographically. Undefined values, non-finite numbers, unsafe integers, duplicate semantic references, cyclic values, and unpaired Unicode surrogates MUST be rejected.

Large integers such as satoshi counters MUST be encoded as canonical decimal strings.

## Identity

Version 1 uses Ed25519. A key identifier is:

`ed25519:SHA256(DER-SPKI-public-key)`

A verifier MUST derive the key identifier from the supplied public key and reject mismatches.

## Statement identifier

`statementId = "sha256:" || SHA256("btc-ai:statement:v1" || 0x00 || canonical(statement))`

## Signed envelope

The signature input is:

`"btc-ai:signed-envelope:v1" || 0x00 || canonical({statementId, statement, signer})`

The envelope signature MUST verify before any statement-specific validation occurs.

## Provenance receipts

A receipt statement MUST include its type, version, namespace, sequence, timestamp, action, actor, parent identifiers, input artifacts, output artifacts, execution facts, claims, and optional policy reference.

Parent identifiers MUST be unique and sorted. A complete-lineage verifier MUST reject missing ancestors and cycles.

## Agent policies

A policy binds an authority signer to one session key and includes:

- Validity interval
- Maximum daily spend in satoshis
- Maximum daily action count
- Allowed model identifiers
- Allowed tools
- Allowed targets

An action MUST reference the exact signed policy statement, be signed by the authorized session key, use a strictly increasing nonce, fall inside the validity interval, and satisfy every allowlist and quota.

Version 1 uses UTC calendar-day buckets. It does not call this a sliding 24-hour window.

## Merkle batches

Receipt identifiers MUST be unique and lexicographically sorted before tree construction.

Leaf hashes are:

`SHA256("btc-ai:merkle-leaf:v1" || 0x00 || UTF8(receiptId))`

Internal nodes are:

`SHA256("btc-ai:merkle-node:v1" || 0x00 || left || right)`

An unpaired final node is promoted unchanged. It is not duplicated. Inclusion proofs MUST encode every tree level, including promotion steps.

## Bitcoin commitment

The BAIP version 1 payload is `BAIP || 0x01 || merkleRoot` and MUST be committed in a null-data output. A conforming verifier MUST check:

- Connected Bitcoin chain equals the anchor chain
- Transaction ID resolves
- Required confirmation depth is met
- A transaction output contains the exact BAIP payload

## Privacy

Implementations SHOULD commit digests rather than confidential prompts, personal data, or proprietary model content. Removing public Bitcoin commitments is impossible.

## Versioning

Unknown major statement or commitment versions MUST be rejected. Extensions MUST NOT silently change the meaning of version 1 fields.
